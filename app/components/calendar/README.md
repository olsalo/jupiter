# Calendar structure

`CalendarRoute` owns the route layout and initial server data. `CalendarSchedule` queries bookings and availability, then prepares the visible members, previews and schedule. `CalendarTimeline` renders the shared day, week and mobile timeline. `CalendarTimelineLane` renders one member's bookings and unavailable periods.

`CalendarMemberRows` provides the desktop day alternative selected with `layout=rows`. It shares availability, overlap layout, range selection and booking drag/resize behavior with the column timeline. Members stay on the left, hours stay at the top, and the current-time marker runs vertically in the business timezone. Mobile continues to use the column day view.

Controls, booking panels and drag hooks live in this folder. Shared domain types and pure helpers live in `app/lib/calendar`; library modules do not import calendar UI components. Forms continue to use RVF and tRPC mutations.

`CalendarAgenda` queries the full selected week for list view, including cancelled bookings, and filters by the selected team member. `CalendarAgendaContent` groups bookings under sticky date headings and opens the same booking editor as the timeline. Desktop scrolling stays within the agenda; mobile uses the page scroll. List navigation follows the business week start and timezone.

During a drag, only the floating card is visible and the matching grid card stays hidden. The floating card updates each animation frame through its preview store. Lane geometry is reused until the layout changes, and scrolling adjusts those cached bounds. The booking panel receives the latest selection after a 120 ms pause or immediately on drop. Drop and cancellation clear pending panel updates. Booking issue markers and the issue list evaluate the current preview position against cached schedule windows. The issue list subscribes directly to the shared pointer preview store, so warnings update immediately without rebuilding the form.

The appointment layout loads the booking and renders its child route. Both the appointment index and edit route use the booking editor, including changing its time. There is no separate appointment reschedule route. Public booking rescheduling remains separate.

The calendar uses a 15-minute grid and initial selection steps, with a 15-minute minimum duration and shared service-based duration steps. Bookings can be resized below the service’s default length. `CalendarTimeline` and `CalendarMemberRows` accept `intervalMinutes` and `minDurationMinutes` props, forwarded to range selection and booking movement/resizing. `BookingDurationField` exposes `minLength` and `intervalMinutes` for its duration controls.

Booking movement also snaps to the exact free edge before or after a neighbouring booking, including service preparation and cleanup buffers. These starts may fall outside the regular 15-minute grid. Resizing keeps the start fixed and offers the current booking duration and the next occupied boundary as additional stops, while preserving the 15-minute minimum. Calendar query results and cached bookings retain buffers so column and row layouts use the same boundaries.

Availability includes valid starts immediately before and after occupied periods, alongside the regular grid. All candidates pass the same working-hours, buffer, break, notice and overlap checks. Public booking suggestions put adjacent starts first within each day; staff time lists remain chronological. Exact-start checks validate only the requested time.

New booking drags and resizing share `getCalendarBookingDragDuration`. They snap to the 15-minute minimum and all active service durations. Only after the longest configured service do they add 15-minute duration steps. `BookingDurationField` uses the same stops for its buttons and keyboard stepping, while direct typing preserves custom lengths. The current booking length and exact gap boundaries remain additional resize stops. `CalendarSchedule` reads the shared service list query and passes its active durations through both timeline layouts to selection and resize handlers. While services are unavailable, or no eligible service lengths exist, regular duration steps remain available. Moving a booking preserves its length.

New drafts match their length to an active service and prefer the service with the most bookings when several match. `service.bookingUsage` returns business-scoped counts excluding cancelled and missed bookings. A new flow without a specified length starts with the most-used active service and its default length. Custom lengths leave the service unselected and are preserved when a service is chosen; choosing a service for a standard length applies its default duration. Explicit service choices remain selected until the draft length changes. Counts are invalidated after booking saves.

The calendar shares its length-based service suggestion with new-range cards and the floating creation draft. Their service name and colour update during pointer movement, without waiting for the panel update or release. Custom lengths use the neutral draft style. Saved bookings retain their service when resized, and cancellation restores the original style.

Typing, pasting or clearing a booking length preserves the current service selection, including an empty selection. Picker steps and new drag lengths still use automatic service suggestions.

Initial range selection retains exact neighbouring booking boundaries, including their buffers, so off-grid gaps are available from the first drag. Increasing the duration picker to its available gap boundary reports a snap separately from a regular duration step and preserves the selected service.

Existing booking moves use minute-precise starts while retaining nearby booking-edge snapping. Resizing keeps the original start and member fixed. Availability validates and includes a selected off-grid start even without a break overlap. The editor keeps its current member when choosing replacement times after a duration change; another member is selected only through an explicit member filter, time-slot choice or cross-member drag.

The availability sheet uses a compact schedule selector with the current schedule and a group of dated upcoming changes. The apply-from date sits beside it on desktop, and the weekly editor stays directly below. Selecting an upcoming change reveals its delete action next to the selector. Working hours and breaks have independent forms, effective dates and lists of upcoming changes. Saving, moving or deleting a change only affects the selected kind. `availability.deleteScheduledChange` permits only future business-local dates, checks the same member access as saving, and reconnects the preceding version of that schedule while retaining later changes. The optional kind parameter keeps older callers compatible. Saving and deletion invalidate calendar availability and booking issue queries. Break cards use a shared brown palette in both calendar layouts and colour modes.

The Time off tab in Availability shares the team time off dialog, list rows, validation and `availability.addTimeOff` mutation. Its create dialog starts with empty dates and the selected calendar member, restricts ordinary members to themselves, and preserves calendar filters on close. Existing block-time links open this tab, and the separate calendar action has been removed. Full-day, timed and repeating blocks use the selected member's timezone. `calendarSchedule` expands recurring blocks into unavailable periods, keeping their titles visible in column, row and mobile layouts. The tab lists the selected member’s upcoming and ongoing blocks in date order, showing the next occurrence of each repeating series and offering removal through the shared team menu. Creating or removing time off refreshes the calendar and booking availability queries.

Availability includes an Extra hours tab for one-off shifts outside the weekly schedule. Its nested dialog starts with an empty date and uses the selected member’s timezone. Upcoming extra hours can be removed with confirmation. Members manage their own shifts and managers can choose a member. Existing extra-availability links open this tab, and the separate calendar menu item has been removed. Calendar working windows merge regular and extra hours so added evenings and weekends appear without duplicated breaks.

Availability tabs use two columns on narrow screens so all four sections fit without horizontal scrolling. The time off empty state centers within the remaining panel space without a fixed minimum height.

Extra hours uses the same upcoming-list header, add button, row spacing, time badges, actions menu and centered empty state as Time off.
